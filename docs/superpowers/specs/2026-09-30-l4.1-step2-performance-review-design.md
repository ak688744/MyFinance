# L4.1 Step 2 — Performance Review (Diagnose → Prescribe → Converse) — Design

**Date:** 2026-09-30 · **Tier:** T1 · **Branch:** `feat/investment-performance-insights` (stacks on `feat/investment-analyzer`)
**Builds on:** `2026-09-06-l4.1-investment-analyzer-agent-design.md` (v1 health analysis). Pulls forward that spec's §10 items *benchmark-relative performance*, *rolling-returns + risk-stats*, *code-execution sandbox* and a bounded form of *whole-market screening*.

---

## 1. Intent

The user wants insights that do more than describe the portfolio. They should:

1. **Diagnose**: say which funds are dragging and which are working, against the fund's benchmark, its category and its risk.
2. **Prescribe**: say what could be done, looking at other funds and other categories.
3. **Converse**: answer follow-up questions with real numbers.

The output is **analysis for the user to act on themselves**: options with their trade-offs, never "sell X, buy Y" orders. Every surface carries a "not advice, verify before acting" line, and tax figures are flagged for verification with a tax professional.

### Grounding: the Claude-with-tools experiment (2026-09-30)
A throwaway experiment (scratchpad only) gave Claude Code the user's real data plus code execution and asked for a portfolio review. Findings that shape this design:

- **The judgement was the valuable part, not the thresholds.** It:
  - distrusted the data, and caught two wrong AMFI codes by cross-checking purchase NAVs (fixed in a separate task);
  - separated 1-year blips (Motilal Midcap: weak 1y, top 3y/5y) from persistent lag (SBI Small Cap beat its index in 4% of the last 24 rolling 3-year windows);
  - picked the right yardstick per fund (arbitrage judged against liquid funds);
  - converted results into ₹ through cash-flow replay;
  - applied lock-in, tax and exit-load limits.
- **The tools it needed were generic:**
  - NAV history for any fund;
  - the category universe (from AMFI's full NAV list);
  - index-fund proxies for benchmarks;
  - transactions and purchase lots;
  - code execution.

  About 250 lines of ad-hoc Python recur as a small set of calculators.
- **Hard rules are worth keeping only as fact checks** (NAV cross-check, exact tax and lock-in), not as judgement ("lagging = X% below the benchmark").

**Architectural principle:** tools supply data and exact maths; the LLM makes the judgements.

## 2. Goals / Non-Goals

**Goals**
- A performance spine over the Direct-Growth mutual-fund universe (~1,750 funds) with benchmark proxies and category statistics.
- Tested deterministic calculators: returns, risk, relative performance, cash-flow replay, lots/tax/lock-in, Regular-vs-Direct drag.
- A cached monthly **LLM portfolio review** that writes the insight cards, with a guard against invented numbers.
- Investment-agent chat tools that include a sandboxed Python escape hatch.

**Non-Goals**
- Automated trades or orders.
- Goal-planning or projection surfaces (the inflation projection stays deferred).
- AUM and expense-ratio screening across the whole universe (only shortlisted funds get tier C data).
- A sandbox for other agents.
- Fixing survivorship bias.
- Storing a directory of all AMFI plans.

## 3. Locked Decisions

- **D1 — Architecture.** Deterministic data and calculators, with LLM judgement on top. There are no threshold rules for "dragging" or "working". Hard-coded logic is limited to fact checks and exact tax, lock-in and exit-load maths.
- **D2 — Universe.** All open-ended **Direct-Growth** plans from AMFI's full NAV list (`portal.amfiindia.com/spages/NAVAll.txt`, ~1,750 funds).
  - Excluded by default: ETFs (they need a demat account), segregated portfolios, and close-ended or interval schemes.
  - Funds with under 3 years of history are listed but not ranked.
- **D3 — No plan directory.** Owned plans resolve their AMFI codes through the existing on-demand search, which is how the ABSL ELSS Regular plan resolves. A Regular plan's Direct twin is also found on demand, by name and AMC.
- **D4 — The universe is a disposable cache.** Each monthly refresh downloads the list, filters it, pulls histories, recomputes stats in memory and **replaces all universe rows in one transaction** (§4). Merged or closed funds disappear on the next build, so there is no per-row deletion logic.
- **D5 — Three data tiers.**
  - **A** (Direct-Growth list): code, name, AMC, category, latest NAV.
  - **B** (performance): **month-end** NAV history for the universe (~120 points per fund) and the stats derived from it.
  - **C** (deep): **daily** NAV plus Groww holdings, expense ratio, AUM, exit load and lock-in. Only for owned funds, benchmark proxies and shortlisted candidates.
  - Groww is never scraped at universe scale.
- **D6 — Benchmarks are index-fund proxies.** Each benchmark is represented by the longest-history Direct index fund tracking it:

  | Benchmark | Proxy fund |
  |---|---|
  | Nifty 50 | 120716 (UTI) |
  | Nifty 100 | 147666 (Axis) |
  | Nifty 500 | 147625 (Motilal Oswal) |
  | Nifty Midcap 150 | 147622 (Motilal Oswal) |
  | Nifty Smallcap 250 | 147623 (Motilal Oswal) |

  - Proxies understate the index by their cost (~0.1–0.3% a year). This is conservative and documented.
  - Arbitrage and liquid-type funds are judged against the **liquid-category median**.
  - Each AMFI category maps to one default proxy (for example Large Cap → Nifty 100, Flexi Cap/ELSS/Large & Mid Cap → Nifty 500). The fact sheet records which proxy was used. Mapping from Groww's `benchmark_name` is deferred, because the category default matched every owned fund in the experiment.
- **D7 — Calculators live in `core/domain/performance/`** as pure TypeScript functions. They are the single implementation, used by the fact sheet, the MCP tools and the sandbox bridge.
- **D8 — The review is an LLM task.** A new `investment_review` AI task, routed to Opus. It runs on the fact sheet, **not** the sandbox, so its output is reproducible. It is cached by signature. The **number guard** rejects any card containing a figure that isn't in the fact sheet.
- **D9 — Sandbox = Pyodide plus a narrow bridge,** investment agent only, and only in chat.
  - It runs in a `worker_thread` with the `js` module blocked, no network, a 30 s timeout and a memory cap.
  - The calculators are registered as a Python `myfinance` module.
  - Data enters only through named datasets.
  - It starts on the first `run_python` call and is terminated after about 10 minutes idle.
- **D10 — Phasing.** **2a** covers the universe, calculators, fact sheet, review cards and deterministic chat tools. **2b** covers the sandbox and `run_python`. 2a ships without waiting on 2b.
- **D11 — Tax rules are one dated constant.** Short-term 20% (held under 1 year); long-term 12.5% above ₹1.25L a year; ELSS lock-in 3 years. They sit in a single `TAX_RULES` constant with an `effectiveFrom` date.

## 4. Data Model (additive `core` tables, migration `0011_performance_universe`)

**`fund_universe`** (tier A and B metadata, rebuilt monthly)
- `amfi_code` (PK), `scheme_name`, `amc`, `category` (normalised, see §5), `latest_nav`, `latest_nav_date`
- `history_start` (first NAV date), `rankable` (history of 3 years or more), `built_at`

**`fund_monthly_nav`** (tier B, rebuilt monthly)
- `amfi_code`, `month_end` (ISO date), `nav`. PK `(amfi_code, month_end)`.

**`fund_performance`** (tier B stats, rebuilt monthly, one row per fund)
- `amfi_code` (PK), `as_of`
- `benchmark_code`: the proxy it was measured against
- trailing returns `r1y, r3y, r5y, r10y`
- `vol_3y`, `max_drawdown_5y`
- `rolling3y_beat_pct`, `rolling3y_median_excess` (over the last 24 monthly windows)
- `up_capture_3y`, `down_capture_3y`
- `category_pctile_3y`, `category_pctile_5y`

**`category_stats`** (rebuilt monthly)
- `category`, `metric`, `p25`, `median`, `p75`, `n`, `as_of`. PK `(category, metric)`.

**`investment_review_cache`**
- `signature` (PK), `review_json`, `model`, `created_at`

**Tier C**
- Reuses v1's `scheme_fundamentals` and `scheme_holdings` for owned funds.
- Daily NAV stays fetched on demand through `getNAVHistory`, with an in-process cache as today. **No daily-NAV table.**
- Candidate funds (not owned) have no `investment_schemes` row, so on-demand tier C details for candidates are cached in a new `candidate_details` table (`amfi_code` PK, `details_json`, `fetched_at`). The same retention idea applies: prune rows older than 90 days on refresh.

**Rebuild mechanics (D4).** Compute the whole new universe in memory first (no DB writes during the slow fetch phase). Then, in **one transaction**, delete the rows of `fund_universe`, `fund_monthly_nav`, `fund_performance` and `category_stats` and insert the new rows. The DB runs in WAL mode (`client.ts`), so readers keep seeing the last committed universe until the commit, and never see a half-built one. This gives the same guarantee as swapping staging tables with less machinery. Money, rates and NAVs are REAL, per the L0 decision.

All tables are additive. Nothing in `xirr.ts`, `portfolio.ts`, `returns.ts` or `categorize.ts` changes.

## 5. Ingestion

**`refreshUniverse(deps)`** lives in `core/domain/performance/universe.ts`. It is an orchestrator like `ingestFundData`:
1. **Download** AMFI's full NAV list with one request.
2. **Parse and filter.**
   - Line format: `code;isin;isin2;name;plan;option;nav;date` under `Open Ended Schemes(<category>)` headers.
   - Normalise categories: both "Equity Scheme - X" and "Equity Schemes - X" map to the same key, and the ELSS spellings are unified.
   - Keep Direct-Growth plans and apply the D2 exclusions.
3. **Fetch** each fund's history from mfapi with bounded concurrency (8). A fetch that fails keeps the fund in `fund_universe` with `rankable=false` and adds no stats. Downsample the history to month-end points.
4. **Compute** per-fund stats against the category's default proxy, then category stats.
5. **Swap** in one transaction (D4).

**Scale and cadence**
- About 140 MB downloaded and 10–15 minutes per run.
- Triggered monthly, from the existing once-per-24h auto-refresh check when `built_at` is more than 30 days old, or manually through a refresh endpoint.
- The run happens in the background and never blocks a request. Status is exposed through the coverage endpoint.

**Injectable fetchers.** The same pattern as `marketData` and `fundData`, so tests never touch the network.

**Seam invariant.** Only global `fetch` is used in `core/domain`. There are no drizzle or better-sqlite3 imports. The repos own the SQL.

## 6. Calculators (`core/domain/performance/`, pure, tested against textbook examples)

| Module | Functions |
|---|---|
| `returns.ts` | `trailingReturn(series, asOf, years)`, `rollingReturns(series, windowYears, stepMonths, spanMonths)`, `relativeRolling(fund, bench, …)` → `{ beatPct, medianExcess, windows }` |
| `risk.ts` | `maxDrawdown(series, from)`, `annualVol(series, years)`, `captureRatios(fund, bench, years)` → `{ up, down }` |
| `category.ts` | `quantiles(values)`, `percentileOf(value, values)` |
| `replay.ts` | `replayCashflows(txns, targetSeries, asOf)` → `{ actualXirr, replayXirr, actualValue, replayValue, diffInr }`. **Imports `calculateXIRR` from `xirr.ts` without modifying it.** |
| `lots.ts` | `buildLots(txns)` (first-in first-out, redemptions consume the oldest lots), `classifyLots(lots, nav, asOf, rules)` → short-term and long-term gains, ELSS locked value, value inside the exit-load window, `estimateExitCost(...)` |
| `planDrag.ts` | `regularDirectDrag(regularSeries, directSeries, years)` → yearly % and ₹ drag |

**Series type:** `{ date: string; nav: number }[]`, sorted ascending.

**Conventions.**
- A NAV lookup takes the latest value on or before the date, and must be within 10 days of it, otherwise `null`.
- Returns are fractions internally. Field names follow the v1 unit-label conventions (`*Pct`, `*Inr`, `*Fraction`).
- Year fractions use days/365, matching `xirr.ts`.

The **fact sheet** is built by `buildFactSheet(deps)` in `core/domain/performance/factSheet.ts`. For each owned fund it assembles:
- tier B stats, its category's stats and tier C details;
- the fund's own figures: replay against its benchmark proxy, lots and tax, and Regular-plan drag where it applies;
- up to 5 candidates in the same category: rankable funds ordered by `rolling3y_median_excess`, each marked `recencyBiased: true`.

Portfolio-level facts come from v1 (inferred profile, overlap, concentration). The sheet also carries summaries for every category and data-quality flags, such as NAV mismatches from the AMFI-code validation task. Every number gets a stable path (for example `funds[3].rolling3yBeatPct`) so the number guard can check it.

## 7. The Review (`investment_review` task)

**Signature.** A hash of: owned scheme ids with their units rounded to 2 dp, `fund_universe.built_at`, the tier C `fetched_at` values for owned funds, the inferred profile label and a prompt version. The same signature means the cached review is served and no LLM call is made.

**Call.** One `gateway.runTask('investment_review', …)` call. That produces one `ai_usage_events` row. The prompt includes the fact sheet as JSON, and the instructions encode the judgement the experiment showed:
- tell persistent lag apart from blips;
- pick the right yardstick for each fund;
- quantify in ₹;
- apply lock-in and tax before any "consider" option;
- flag recency bias on candidates;
- never phrase a card as a directive.

**Output (Zod).**
```
{ cards: [{ kind: 'dragging'|'working'|'consider'|'data_quality',
            title, detail, fundIds: number[], impactInr?: number,
            evidence: string[],   // fact-sheet paths
            discussPrompt: string }],
  summary: string }
```

**Number guard.** The guard extracts every number in `title`, `detail`, `summary` and `impactInr`:
- ₹ amounts, percentages and plain numbers;
- lakh and crore forms such as ₹1.39L, normalised before comparison.

Each must match some fact-sheet value within tolerance: 0.1 percentage points for percentages, and 1% or ₹1 (whichever is larger) for money. Small integers of 12 or less are exempt, as counts and months. A card that fails gets one retry of the whole review, with the failing cards named. If it fails again, that card is dropped. Cards whose `evidence` paths don't resolve are dropped too.

**Failure fallback.** If there is no route, a provider error, bad JSON after one retry, or the universe hasn't been built yet, the endpoint returns `{ cards: [], reviewUnavailable: true, reason }`. The web app then renders the v1 deterministic cards it already fetches from `/investments/analysis/insights`, so the page is never blank. Failed reviews are **not** cached, following the lesson from the expense-triage fix.

**API.** `GET /investments/review` → `{ cards, summary, asOf, cached, reviewUnavailable? }`. `POST /investments/universe/refresh` starts the background rebuild, and the existing coverage endpoint gains universe status.

**UI.**
- The header "AI Insights / LIVE" is replaced by **"Portfolio review"** with the AI marker and an as-of date.
- The layout has four lanes: **Dragging**, **Working**, **Consider**, **Data issues**. The v1 profile card stays on top.
- Each card has a **Discuss** button that opens the existing investment drawer, seeded with `discussPrompt`.
- A standing footnote: "Analysis, not advice. Tax figures are estimates, verify before acting."

## 8. Agent Tools

**Phase 2a** adds deterministic tools. They are MCP read tools, plus one write-ish tool, added to `INVESTMENT_TOOL_ALLOWLIST`:

| Tool | Returns |
|---|---|
| `get_fund_performance({ codes })` | `fund_performance` rows (tier B) |
| `compare_to_benchmark({ code, windowYears? })` | Relative rolling, capture, drawdown vs its proxy (computed live from month-end NAVs) |
| `get_category_stats({ category })` | `category_stats` rows |
| `screen_category({ category, minHistoryYears?, sortBy, limit? })` | Rankable universe funds with stats (maximum `limit` 25) |
| `replay_cashflows({ schemeId, targetCode })` | `replayCashflows` output |
| `get_lots_and_tax({ schemeId })` | `classifyLots` output with `TAX_RULES.effectiveFrom` |
| `estimate_switch_cost({ schemeId, units? })` | Tax plus exit load for a hypothetical exit |
| `fetch_fund_details({ code })` | Tier C on demand (Groww plus daily NAV), cached in `candidate_details` |

**Phase 2b** adds `run_python({ code, datasets })`:
- **Datasets:**
  - `nav:<code>`: daily for tier C, otherwise month-end;
  - `universe_stats`, `category_stats`;
  - `transactions:<schemeId>`;
  - `fact_sheet`.
- **Returns** `{ stdout, result, error?, durationMs }`. The code and its output are kept with the chat message for provenance, shown as an expandable "how this was computed" section.
- **Limits:** 30 s timeout, output truncated at 20 KB.

**Instruction additions** (`INVESTMENT_INSTRUCTIONS`):
- every number must come from a tool result;
- call out recency bias when citing candidates;
- check lock-in and tax (`get_lots_and_tax`) before discussing any exit;
- options, not directives;
- prefer the deterministic tools and use `run_python` only for questions they can't answer.

## 9. Sandbox (Phase 2b)

- **Runtime.**
  - `pyodide` (npm), loaded in a dedicated `worker_thread` owned by `packages/agent-harness` (new `sandbox/`).
  - Preloaded packages: numpy and pandas.
  - Started lazily; one worker per chat session; terminated after 10 minutes idle.
- **Isolation.**
  - Before any user code runs: remove `js` and `pyodide_js` from `sys.modules` and block importing them. Disable `pyodide.http` and `micropip`. Give the worker no network.
  - Timeout: the host calls `worker.terminate()` at 30 s.
  - Memory: the worker's `resourceLimits` cap it at 512 MB.
  - Fund-page text never reaches the sandbox as code, only as data.
- **Bridge.** The host registers a single `myfinance` module whose functions are **proxies for the TypeScript calculators**. Arguments are serialised in, computed on the host side by the tested functions, and results serialised back. No other host object is reachable.
- **Datasets.** The tool handler resolves the named datasets through the same repos and fetchers as the tools and writes them into the worker's in-memory filesystem as JSON or CSV. The sandbox has no DB handle.

## 10. Error Handling

- **Universe refresh.** A failed AMFI download or parse aborts the rebuild and keeps the previous tables. mfapi failures for individual funds are tolerated, since those funds are marked not rankable. If more than 20% of funds fail, the rebuild is aborted.
- **Benchmark proxy missing or too short.** Relative metrics become `null`, the fact sheet notes it, and the review is told not to judge on those metrics.
- **Funds lacking data.** A fund with no transactions (ABSL today) gets lots, tax and replay marked `unavailable: 'no transactions'` rather than zero.
- **Review.** See the §7 fallback. Tool errors go through `errorResult` as they do today.
- **Sandbox.** Timeouts, memory kills and Python exceptions come back as a normal tool result carrying `error`, and a killed worker is restarted on the next call.

## 11. Testing & T1 Gates

- **Groww golden-master 6/6 unchanged.** `git diff` must show no changes to `xirr.ts`, `portfolio.ts`, `returns.ts` or `categorize.ts`.
- **Calculators.** Textbook fixtures: known-CAGR series; drawdown on a crafted V-shaped series; capture ratios on a synthetic fund/benchmark pair; replay where the target equals the source (the difference must be 0); lots with partial redemptions; tax boundaries at 365 days and 3 years, and the ₹1.25L exemption.
- **Universe.** A parse test against a trimmed real NAV-list fixture, covering both header styles, IDCW/Regular/segregated exclusions and category normalisation. Also a rebuild-swap test: a failed build leaves the old tables intact.
- **Fact sheet and review.** Fact-sheet snapshot tests on fixture repos. Number-guard unit tests: an invented number is caught; lakh/crore and percentage forms are normalised; small integers are exempt. Review service tests use a fake gateway covering a cache hit, the fallback and "failed reviews not cached".
- **Tools and API.** Tests with injected offline fetchers, like v1.
- **Sandbox (2b).**
  - **Isolation:** `import js` fails; network access fails; an infinite loop is killed at 30 s; excessive memory use kills the worker.
  - **Bridge and datasets:** a bridge call returns the same value as the TypeScript function, and datasets load correctly.
- **Quality evals (manual, documented).** About 8 saved questions with known answers from the 2026-09-30 experiment, for example "does SBI Small Cap lag persistently?" and "what did my Axis ELSS SIPs cost me against Nifty 500?". Rerun after prompt changes.
- **Seam invariant.** No drizzle or better-sqlite3 imports in `core/domain/performance`, `agent-harness/src` or the sandbox. Full suite green on Node 22.
