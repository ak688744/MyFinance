# L4.1 — Investment Analyzer Agent (v1: Portfolio Health) — Design

**Date:** 2026-09-06
**Tier:** T1 (new specialist agent + new market-data ingestion surface + new `core` schema/domain). Groww golden-master is a **standing invariant** — the change is additive and touches no XIRR/portfolio/categorize/NAV math, so no re-derivation, but the gate must stay 6/6.
**Status:** Brainstorm complete — spec for review. No code yet.
**Layer:** First specialist slice of **L4.1** (orchestrator + expense/investment/loan specialists). The Expense Clarity Agent was the earlier slice; this is the **investment specialist**.

---

## 1. Context & North Star

The MASTER_PLAN §1 names the "Investment Analyzer" — *gather MF holdings → compute sector split → tell me what's doing well/badly and what helps/hurts* — as the canonical agent. This spec builds its **v1: a health analysis of the user's current mutual-fund holdings**, with a data spine and agent shaped so that **whole-market fund recommendation** (the eventual end goal) is a later ingestion-breadth + stats extension, not a redesign.

Two capabilities were identified; they share a fund-fundamentals data spine but differ enormously in data *breadth*:
1. **Portfolio health analysis** (owned funds) — overlap, concentration, allocation, cost, goal-fit. Needs rich data for only the ~8 funds owned + benchmarks. **← v1.**
2. **Market-wide recommendation** — needs the same rich data for the whole ~1,500-fund universe, kept fresh. **← deferred (phase 2).**

### Grounding research (this session, two parallel agents)

**Data-source ground truth:** There is **no free, turnkey, machine-readable feed of Indian fund holdings/sector.** NAV/returns/expense/category are free and easy; **holdings + sector — exactly what overlap needs — are the hard part.** Real paths:
- **Official AMC monthly portfolio XLSX** (SEBI Master Circular Ch. 6.1.1, Format 4C — published within 10 days of month-end as a downloadable spreadsheet). ToS-clean, high effort (per-AMC layouts), scales poorly.
- **Unofficial platform JSON** — **Groww's embedded `__NEXT_DATA__`** is the richest single payload (holdings + sector + Sharpe/beta/SD/alpha + expense + returns + benchmark + peers); **Tickertape** holdings/sector JSON (no auth); **Kuvera** clean JSON for expense/returns/AUM/category (no holdings). Low effort, **ToS prohibits automated use** (acceptable-risk for a private single-user monthly-cadence fetch).
- **Paid** (Morningstar/Value Research) — overkill/licensing risk for single-user.

Crucially, the unofficial payloads are **already structured JSON** → fetch+parse is **deterministic** (Zod-validated), *no LLM needed*. LLM extraction is only required for the messy AMC-XLSX path.

**Methodology ground truth:** The high-value v1 analyses (overlap, look-through allocation, concentration, cost, redundancy, goal-fit) are all **deterministic weighted arithmetic over holdings data** — trivial pure functions, no stats environment. The stats-heavy metrics (rolling returns, Sharpe/Sortino/beta/alpha/capture) genuinely need a flexible numeric environment **and** a second data dependency (benchmark index + risk-free series) — they form a clean **phase 2**. Overlap = **Σ over common stocks min(w_A, w_B)**; >50% is the redundancy flag. Allocation roll-up is weighted by **current market value** (units × NAV), then by each fund's internal bucket weights. Market-cap buckets use the SEBI/AMFI definition (large = top 100, mid = 101–250, small = 251+).

## 2. Goals / Non-Goals

**Goals (v1):**
- Store fund fundamentals + holdings for the user's owned funds.
- Deterministic analysis functions (overlap, look-through allocation, concentration, redundancy, cost, goal-fit) in `core`, exposed via MCP read tools + REST.
- An **Investment Analyzer specialist agent** that reasons over verified numbers, captures goals/risk in conversation, and can **refresh fund data itself** via a deterministic MCP tool.
- **Deterministic MF insight cards** on the Investments page + a **Discuss** chat drawer.

**Non-Goals (v1 — deferred, §10):** rolling-returns & risk-stats suite; the code-execution sandbox; benchmark/risk-free data ingestion; whole-market screening/recommendation; AMC-XLSX file-import (LLM) fallback; static analysis dashboards (heatmaps/donuts); a structured goals/risk-profile schema.

---

## 3. Locked Decisions

- **D1 — v1 = health analysis of owned funds; end goal = both.** Design the data spine + agent so market-wide screening is an ingestion-breadth + stats extension later.
- **D2 — Data source = unofficial platform JSON, agent-driven fetch.** Groww `__NEXT_DATA__` primary (holdings + sector + risk + expense + returns in one), Tickertape as holdings/sector cross-check, Kuvera as expense/returns/AUM fallback. NAV history stays on `api.mfapi.in`. ToS caveat documented; acceptable for private single-user monthly-cadence use.
- **D3 — Ingestion is deterministic (no LLM/gateway in v1).** Unofficial payloads are structured JSON → parse + Zod-validate. **AMC-XLSX file-import (which would need the LLM gateway) is dropped from v1.**
- **D4 — The agent fetches/refreshes data itself** via an MCP `refresh_fund_data` tool (network + repo-write inside the MCP process, like existing `marketData` + write tools). A REST endpoint triggers the same core ingest for a UI "refresh" convenience.
- **D5 — Compute = pre-built deterministic `core` functions in v1; sandbox deferred.** v1's whole value is weighted arithmetic over a tiny holdings dataset → tested pure functions (golden-style). The Pyodide code-execution sandbox earns its keep only in phase 2 (rolling-returns distributions + risk regressions), which also share phase 2's benchmark-data dependency. The agent reasons over verified tool outputs and never does the arithmetic itself; **already-validated XIRR/portfolio numbers are handed in as ground truth, never recomputed.**
- **D6 — Holdings storage = history-capable schema, latest-only in v1 + retention cap.** Key `(schemeId, asOfDate)`; v1 writes/reads the latest snapshot per scheme; prune to the last ~12 as-of dates per scheme. Bounded growth; free monthly history for phase-2 trends; no future migration.
- **D7 — Goals/risk captured in-conversation, stored in agent memory** (no new schema) — the agent asks via `ask_user` and persists to its isolated Mastra memory resource.
- **D8 — UX = deterministic MF insight cards + Discuss chat drawer** (reuse the expense-insights → drawer pattern). Detectors are precise (overlap/concentration/cost), so **no LLM triage layer** (unlike expense `new_spend`). Static analysis dashboards deferred.
- **D9 — Additive `core` schema only; Groww untouched.** New tables reference `investment_schemes`; no XIRR/portfolio/categorize/NAV code changes. Golden-master 6/6 unchanged is the gate.

## 4. Data Model (additive `core` tables)

`investment_schemes` already carries `schemeName`, `amfiCode`, `isin`, `amcName`, `category` (`equity|debt|hybrid|other`), `subCategory`. Owned funds are discovered from `investment_transactions → investment_schemes`.

Two new tables (all money/rate/weight fields **REAL**, per the L0 money decision):

**`scheme_fundamentals`** — one latest row per scheme:
- `schemeId` (FK → `investment_schemes.id`, unique)
- `expenseRatioDirect`, `expenseRatioRegular` (REAL, nullable)
- `planType` (`direct|regular|unknown`, nullable — the user's own held plan; derived where possible)
- `aum` (REAL, nullable)
- `benchmarkName` (text, nullable)
- risk fields (nullable, populated opportunistically from Groww but **not** analyzed in v1): `stdDev`, `sharpe`, `beta`, `alpha`
- `source` (text — e.g. `groww|tickertape|kuvera`), `fetchedAt` (ISO text)

**`scheme_holdings`** — per `(schemeId, asOfDate, security)`:
- `schemeId` (FK), `asOfDate` (ISO text — the disclosure month)
- `securityName` (text), `isin` (text, nullable)
- `weightPct` (REAL — % of the fund's net assets)
- `sector` (text, nullable), `marketCapBucket` (`large|mid|small|other`, nullable)
- index on `(schemeId, asOfDate)`.

**Retention:** on write, keep the last ~12 distinct `asOfDate`s per scheme, prune older (a bounded, non-financial housekeeping step).

New repos: `schemeFundamentalsRepo` (upsert-latest, get), `schemeHoldingsRepo` (replace-snapshot for `(schemeId, asOfDate)`, getLatestSnapshot, listOwnedCoverage, prune). Repos own all SQL (L0 seam).

## 5. Ingestion (deterministic, agent-driven)

**Fetch adapters** — `core/domain/fundData/` (pure `fetch` clients, mirroring `domain/nav/navService`):
- `groww.ts` (primary — parse embedded `__NEXT_DATA__` JSON), `tickertape.ts` (holdings/sector cross-check), `kuvera.ts` (expense/returns/AUM fallback).
- A small **adapter registry** `resolveFundDataAdapter(source)` mirroring the L1 parser-registry seam (drop-in new sources).
- Each adapter returns a normalized `FetchedFundData { fundamentals, holdings[], asOfDate, source }`; a `mergeFundData` combines them (Groww primary; Tickertape fills holdings gaps; Kuvera fills expense/AUM). Zod-validated; on shape break, that source errors out cleanly (transient).

**Orchestrator** — `ingestFundData({ adapters, schemeRepo, fundamentalsRepo, holdingsRepo, runInTransaction }, amfiCode)`: fetch → merge → validate → write fundamentals (upsert-latest) + holdings (replace snapshot) + prune, atomically. Injectable adapters so tests run offline against **captured, PII-free sample fixtures**.

**Surfaces:**
- **MCP write/fetch tool `refresh_fund_data({ amfiCode, source? })`** — the agent's path. Handler calls `ingestFundData` inside the MCP process. Network + repo-write both already precedented in MCP (`marketData` network; write tools + `runInTransaction`). The fetcher is injected into `McpContext` like `marketData`.
- **REST `POST /investments/fund-data/refresh`** (single or bulk-owned) — shares the same `ingestFundData` core function; a UI convenience.

No gateway/LLM anywhere in the v1 fund-data path.

## 6. Analysis Engine (pure `core/domain`, tested golden-style)

`core/domain/investmentAnalysis/` — pure functions over stored holdings + owned-fund current values (units × NAV, reusing existing portfolio/NAV reads for value; **XIRR/returns handed in, never recomputed**):
- `overlap.ts` — pairwise `Σ min(w_A, w_B)` on common securities; returns matrix + common-security lists. Redundancy flag at >50%.
- `lookthrough.ts` — weighted roll-up (by current value × fund-internal weights) across **sector**, **market-cap bucket**, **asset class**, and **single security** (hidden cross-fund concentration).
- `concentration.ts` — per-fund + portfolio top-N weight, single-stock max, sector concentration, HHI (`Σ wᵢ²`).
- `redundancy.ts` — same-category counts (≥N) + high-overlap pairs.
- `goalFit.ts` — horizon/risk → allowed-category rules; flags category↔horizon mismatch, redundancy, and (phase-2-ready) laggard hooks.
- `cost.ts` — expense-ratio drag + direct-vs-regular gap estimate.

Each with textbook-fixture unit tests (same discipline as `domain/valuation` and `domain/loans/amortization`). A "no holdings as of X" / stale signal is a first-class return so the agent knows to `refresh_fund_data`.

## 7. Tool & API Surface

**New MCP read tools** (pattern: `run<Name>(ctx,input)` + `register<Name>(server,ctx)`, `ok`/`errorResult`, unit-safe field labels `*Inr`/`*Percent`):
- `get_fund_fundamentals`, `get_portfolio_holdings_status` (coverage/staleness per owned fund), `analyze_fund_overlap`, `get_portfolio_lookthrough`, `analyze_concentration`, `detect_redundancy`, `check_goal_fit`.
- **New MCP write tool** `refresh_fund_data` (§5).
- Reuse existing `get_investment_portfolio` / returns as **ground-truth** inputs.

**New REST endpoints** (feed web UI, share the same domain): `GET /investments/fund-data/coverage`, `GET /investments/analysis/*` (overlap / lookthrough / concentration / insights), `POST /investments/fund-data/refresh`.

## 8. The Investment Analyzer Agent

- `buildInvestmentAgent({ model, memory, tools })` mirroring `buildExpenseAgent`: focused **tool allowlist** (investment + networth read tools + the new analysis tools + `refresh_fund_data` + `ask_user`; **no** expense/loan tools), isolated **memory resource `investment-agent`** (no cross-pollination with wealth/expense recall).
- New `investment_agent` entry in `AI_TASKS` (own DB route, independently priced/routed via AI Settings).
- `runChat({ agent })` extended to `'wealth' | 'expense' | 'investment'` — switches task (`investment_agent`), resourceId (`investment-agent`), builder, and tool set. One `ai_usage_events` row per turn (existing machinery).
- **Instructions:** answer-first, calibrated verbosity (per the existing calibration work); reason over verified tool numbers, never do the arithmetic; when holdings are missing/stale, call `refresh_fund_data` then analyze; capture goals/horizon/risk via `ask_user` and rely on memory; GFM output, tables only when comparing funds.

## 9. UX — Insight cards + Discuss drawer

- **Deterministic MF insight detectors** (`core/domain/investmentAnalysis` + a small assembler) → `GET /investments/analysis/insights` → **insight cards** on the Investments page. Examples: high-overlap pair, single-stock cross-fund concentration, regular-plan cost leak, category over-diversification, allocation-vs-stated-risk drift, stale/missing holdings ("refresh to analyze").
- Cards reuse the expense-insights card pattern (localStorage dismissal) but **without** the LLM triage layer (detectors are precise).
- **Discuss** on a card opens the **Investment Analyzer chat drawer** (`ChatPanel` + `useAgentChat({ agent: 'investment' })`, seeded with the insight), mirroring `ExpensesInsightDrawer`. Free-text + `ask_user` chips as in the expense flow.

## 10. Deferred / Phase 2 (explicitly logged)

- **Code-execution sandbox** (Pyodide) — general L4 capability; unlocks flexible numeric analysis.
- **Rolling-returns + risk-stats suite** (Sharpe/Sortino/beta/alpha/R²/up-down capture, quartiles/consistency) — needs benchmark index + risk-free series ingestion **and** the sandbox.
- **Whole-market screening/recommendation** — broaden ingestion to the ~1,500-fund universe (+ retention/pruning matters at that scale); likely migrate holdings to the official AMC-XLSX parser for ToS-compliance + coverage.
- **AMC-XLSX file-import fallback** (LLM `fund_data_parse` task, multipart) — the ToS-clean acquisition path when unofficial endpoints break.
- **Structured goals/risk-profile schema** (first-class tables + UI) — if goal-planning becomes its own feature.
- **Static analysis dashboards** (overlap heatmap, look-through donut).
- **LLM insight triage** for investments — only if detectors ever prove false-alarm-prone.
