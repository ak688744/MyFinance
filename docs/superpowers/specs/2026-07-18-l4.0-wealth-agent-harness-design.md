## 1. Goal & vision

Build the foundation of a **model-independent finance agent** — "Claude Code, but for finance." The North Star (MASTER_PLAN §1) is a wealth-manager orchestrator delegating to specialist agents, with a **persistent, self-enhancing memory** of the user (profile, needs, goals, future plans) so the user never re-explains themselves.

That full vision is a **program of work**, decomposed into sequential specs:

| Sub-layer | Scope | Status |
|---|---|---|
| **L4.0** (this spec) | Agent **harness** + **memory subsystem** + **one general finance agent** over the 32 MCP read+write tools, reachable via a streaming chat endpoint + web Assistant UI. | This spec |
| **L4.1** | Wealth-manager **orchestrator** + expense/investment/loan **specialist** sub-agents, reusing the harness + memory. | Deferred |
| **L4.2** | **Context/token optimization** (summarization, semantic recall tuning, tool-result trimming). | Deferred |

**Memory is in from day one** (not bolted on) — it is the differentiating capability.

## 2. Framework decision (supersedes a locked master-plan choice)

**Chosen engine: Mastra** (`@mastra/core`), a TypeScript-native agent framework.

MASTER_PLAN §2 locked the **Claude Agent SDK** as the agent engine. **This spec consciously supersedes that** because the user requires the agent to be **model-independent** (routable to any provider — the same philosophy already applied to categorization). The Claude Agent SDK is **Claude-only** (Anthropic API / Bedrock / Vertex) and cannot call Gemini/OpenAI/etc., so it is rejected on the model-independence requirement.

**Why Mastra over alternatives** (evaluated: Claude Agent SDK, Vercel AI SDK, LangGraph.js, Mastra, CrewAI):
- **CrewAI** — Python-only → rejected (polyglot tax on a TS monorepo).
- **Vercel AI SDK** — TS-native, model-independent, MCP-capable, but a low-level primitive: memory, sessions, and multi-agent orchestration are hand-built.
- **LangGraph.js** — powerful graph/state-machine orchestration + persistence, but lower-level and heavyweight for a single chat agent now; its value lands at L4.1.
- **Mastra** — TS-native; the **closest model-independent analog to the Claude Agent SDK's capability set**: agentic loop, subagents/workflows (for L4.1), tool gating, **native MCP client**, and **first-class evolving memory** (working memory + message history + semantic recall). Uses the Vercel AI SDK underneath for provider-independence.

Capability match (closest → farthest to Claude Agent SDK, model-independent only): **Mastra > LangGraph.js > Vercel AI SDK.**

**Accepted risk:** Mastra is younger than the Anthropic SDK and moves fast — the tradeoff for the closest capability match without Claude lock-in.

## 3. Architecture

### 3.1 New package: `packages/agent-harness` (`@myfinance/agent-harness`)

A dedicated package for **agentic** work — distinct from the existing `packages/agents`, which is **LLM plumbing** (the `LlmGateway`, provider adapters, single-shot `categorizeWithAI`). Naming makes the distinction explicit: `agents` = plumbing/single-shot; `agent-harness` = Mastra agents + memory + orchestration (this agent now; orchestrator + specialists in L4.1).

Contents:
- `wealthAgent.ts` — the Mastra `Agent` (persona instructions, model, memory, tools).
- `mcpTools.ts` — a Mastra `MCPClient` pointed at the `packages/mcp` stdio server, exposing all 32 tools to the agent (zero tool rewrite).
- `memory.ts` — Mastra `Memory` config (working memory + history + semantic recall) + the storage backend wiring.
- `modelResolver.ts` — per-turn resolution of the `wealth_chat` route + provider key from the DB (§3.4).
- `runChat.ts` — the streaming callable the API route consumes; also records usage on turn end.
- `index.ts` — public surface.

### 3.2 Two LLM paths (resolves the gateway tension)

The existing `LlmGateway` provides a single-shot `complete(prompt, jsonSchema)` choke point and **cannot** drive an agentic loop (the SDK/framework owns the loop). So L4.0 introduces a **second, parallel LLM path**:

| Path | Engine | Shape | Providers | Use |
|---|---|---|---|---|
| **Gateway** (existing, unchanged) | `LlmGateway` + provider adapters | single-shot structured JSON | any (Gemini/Bedrock/OpenAI) | categorization; future single-shot tasks |
| **Agent** (new) | Mastra | multi-step agentic tool loop | any (Mastra `provider/model`) | conversational wealth agent |

Both are model-independent; they differ in shape (single-shot vs. agentic). They **converge** at two seams: model choice (both read `ai_task_routes`) and usage (both write `ai_usage_events`).

### 3.3 Data flow (one turn)

```
web Assistant chat → POST /agent/chat (packages/api, streaming, SSE)
  → harness.runChat({ resourceId, threadId, message })
    → resolve wealth_chat route + decrypt provider key from DB (per-turn, §3.4)
    → wealthAgent.stream(message, { memory: { resource, thread } })
        ├─ Mastra injects working memory (profile) + recent history + semantic recall
        ├─ model loop calls MCP tools:
        │     reads  → get_networth_overview / get_investment_portfolio / get_expense_summary / …
        │     writes → add_transaction / categorize_transaction / … (preview-gated destructives)
        │       └─ MCP server (stdio) → core repos/domain (the real finance logic)
        ├─ Mastra auto-updates working memory (profile) — surfaced in the reply
        └─ streams tokens → API → web
  → on turn completion: write ONE ai_usage_events row (task='wealth_chat') from Mastra's usage
```

### 3.4 Model + key resolution (per-turn, live pickup)

- **Model is DB-routed:** a new AI task `wealth_chat` is added to the `AI_TASKS` registry; its `ai_task_routes` row selects the provider+model, user-editable in AI Settings. Model is expressed to Mastra as a `'provider/model'` string (Mastra format, e.g. `anthropic/claude-sonnet-4-6`, `google/gemini-2.5-flash`).
- **Keys bridge DB → Mastra:** AI-Settings keys are AES-256-GCM-encrypted in the DB; Mastra resolves keys from env vars per provider. On **each** `runChat` call the harness reads the route, decrypts the provider key via the existing `core` `crypto.ts`, and supplies it to Mastra **per-call if supported, else via a scoped per-turn `process.env` set**. Result: a key/model changed in AI Settings takes effect on the **next message — no restart** (decision: per-turn live pickup).
- **Not-configured** (empty route or missing key) → a clear `provider_not_configured`-style error surfaced in chat (never a raw trace).

> IMPLEMENTATION NOTE: verify whether Mastra accepts a per-call/per-agent API key in the model config. If yes, use it (no global mutation). If no, set `process.env[<PROVIDER_KEY>]` immediately before the call within `runChat` (single-user, serial chat → acceptable shared-state write).

## 4. Memory subsystem

The heart of "don't re-explain myself." **Uses Mastra's native `Memory`** — NOT a proxy through MCP tools (proxying would forfeit Mastra's automatic context injection, autonomous working-memory maintenance, and semantic recall).

### 4.1 Layers
- **Working memory (the profile):** durable structured facts about the user — income, risk tolerance, goals ("retire by 55"), preferences ("count transfers as spend"), future plans. Auto-injected at the start of every turn; **auto-maintained** by Mastra as the conversation evolves.
- **Message history:** per-thread transcript (`resourceId` = the single user, constant; `threadId` = a conversation) for multi-turn continuity.
- **Semantic recall:** vector search over past messages (Postgres + pgvector at convergence).

### 4.2 Storage (Mastra-owned schema, converging on Postgres)
Memory is **Mastra-managed** (its own schema), backed by the **same DB engine the app is migrating to** (MASTER_PLAN: SQLite now → Postgres + pgvector, vectors in the same DB):
- **Now (SQLite phase):** Mastra `LibSQLStore`, as a **separate store file alongside** the `core` SQLite DB. (Running Mastra's LibSQL driver and core's `better-sqlite3` against one file concurrently risks WAL/locking conflicts, so during the SQLite phase they are separate files.)
- **At the planned Postgres migration:** Mastra `PostgresStore` + pgvector in the **same instance** as `core`. This is where the two truly converge to one database (two schemas: `core` owns finance, Mastra owns memory).

**Financial truth stays in `core` repos; memory (profile + threads + vectors) is Mastra-owned.** This revises the earlier brainstorm answer "memory via core repos" — a conscious correction to preserve Mastra's native recall.

### 4.3 Evolution policy — autonomous but surfaced
The agent updates the profile as it learns, and **tells the user what it saved** ("I've noted: retire by 55") so it is visible and correctable. (Not silent; not explicit-only.)

## 5. The agent

- **`instructions` (persona):** a wealth-manager that (1) grounds every answer in the user's profile + live tool data, (2) explains its reasoning, (3) surfaces profile updates, (4) respects the write-tool preview gates — narrates an intended mutation and asks before sending `confirm:true` on destructive ops.
- **`model`:** `'provider/model'` string from the `wealth_chat` route (§3.4).
- **`memory`:** §4.
- **`tools`:** all 32 MCP tools via the Mastra `MCPClient` → `packages/mcp` stdio server. No tool rewrite; the agent gets reads + writes.

## 6. Interface

- **`POST /agent/chat`** in `packages/api` — streaming (SSE), body `{ threadId?, message }` (`resourceId` is the constant single-user id; a new `threadId` is minted if absent and returned). Streams assistant tokens; ends with a completion event carrying `{ threadId, usage }`.
- **Web:** wire the existing `apps/web` **Assistant** page (currently the "Coming in L4" placeholder) to a real chat UI consuming the stream — message list, streaming assistant bubbles, thread continuity, surfaced profile-update notices, and rendering of preview/confirm exchanges for destructive tools.

|---|---|---|
| **D1** | **Mastra** as the agent engine; **supersedes** the master-plan's Claude Agent SDK choice. | User requires model-independence; Claude Agent SDK is Claude-only. Mastra is the closest model-independent analog (memory + subagents + native MCP + gating). |

| **D6** | Memory evolves **autonomously but surfaced**. | No-re-explaining with transparency + correctability. |
| **D7** | Model **DB-routed** via new `wealth_chat` AI task; keys **resolved per-turn (live pickup)** by decrypting the AI-Settings key and passing per-call (or scoped env-set). | User-configurable model/keys in AI Settings; changes apply on the next message, no restart. ## 8. Error handling

- **Not configured** (no `wealth_chat` route / missing key) → clear actionable chat error ("Configure a model for the wealth agent in AI Settings"). Never a raw trace.
- **Provider errors** (rate limit/auth/outage) → caught, surfaced as a chat-level error; turn ends cleanly, no partial corruption.
- **Tool errors** → MCP tools already return `isError`; the agent reacts/retries or reports. Preview-gated writes return their preview; the agent relays and asks before confirming.
- **Stream breakage** → client shows partial output + error; memory + usage recording happen only on turn completion.
